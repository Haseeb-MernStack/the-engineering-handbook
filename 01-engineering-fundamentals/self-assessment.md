# Self-Assessment: Engineering Fundamentals

> Check what you can do today, not what you have read. Each item describes observable behavior. Be strict: if you could not do it in front of a colleague without looking it up, leave it unchecked.

## How to use this page

1. Work through one topic at a time. Check an item only if you can do it **unprompted** and **explain why**.
2. Count the checked items for each topic and use the score guide at the end.
3. Revisit in three to six months. The goal is a shrinking list of unchecked items, not a perfect score.

## The Engineering Mindset

- [ ] Before starting a task, I can state the outcome it serves and how I would know it worked.
- [ ] I can name what could fail in a change I am making, before I make it.
- [ ] I treat cost, security and operability as design inputs, not as later tasks.
- [ ] I can explain the difference between finishing a ticket and owning an outcome.
- [ ] I question a requirement that looks wrong instead of implementing it as written.

## How Computers Work

- [ ] I can describe roughly what happens between pressing a key and a program reacting.
- [ ] I can explain the difference between CPU, memory, disk and network in terms of speed and cost.
- [ ] I can explain why cache locality affects performance.
- [ ] I can explain what a process, a thread and a system call are.
- [ ] I can estimate which resource (CPU, memory, disk, network) is likely to limit a given workload.

## Problem Solving and Debugging

- [ ] I reproduce a bug reliably before I try to fix it.
- [ ] I form a hypothesis, predict what I should observe, and test the prediction.
- [ ] I change one thing at a time while investigating.
- [ ] I can narrow a failure by bisecting, by code, by time, by input or by environment.
- [ ] I find the cause, not only the symptom, and I add a test that would have caught it.
- [ ] I write down what I tried, so I do not repeat work or lose the thread.

## Trade-offs and Decision Making

- [ ] For a design choice, I list at least two real options and what each costs.
- [ ] I can say which constraint (latency, cost, time, risk, team skill) drove a decision.
- [ ] I can tell a reversible decision from an irreversible one and spend effort accordingly.
- [ ] I write short decision records that state context, options, choice and consequences.
- [ ] I revisit a decision when its assumptions change.

## Requirements and Estimation

- [ ] I separate what the user asked for from the problem they are trying to solve.
- [ ] I ask for acceptance criteria and non-functional needs, such as latency, availability and data volume.
- [ ] I give estimates as ranges with stated assumptions.
- [ ] I can do a back-of-the-envelope calculation for load, storage or cost and check it for sanity.
- [ ] I identify the largest unknown in an estimate and reduce it first.

## Reviewing generated code

- [ ] I can explain every line of code I commit, whether I or a tool wrote it.
- [ ] I check generated code against the requirement, not just against whether it runs.
- [ ] I ask what the tool assumed that I did not tell it.

## Score guide

Count the checked items **per topic**.

| Checked in the topic | Where you are | What to do |
| --- | --- | --- |
| All or all but one | Solid | Move on. Test yourself with the [question bank](./question-bank.md). |
| About half | Partial | Reread the topic, then redo the checklist. Apply each unchecked item to a task you are doing this week. |
| Fewer than half | Gap | Start with the topic's **Overview** and **Core Concepts**, then work through its **In Practice** section by hand. |
