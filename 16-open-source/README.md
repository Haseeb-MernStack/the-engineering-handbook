# Open Source

## Overview

Almost every system you will build rests on open source. Your language runtime, your framework, your database driver, your build tool and most of your transitive dependencies were written and are maintained by people outside your company. Understanding how that work happens makes you a better consumer of it: you can judge which dependencies to trust, read licenses without panic, and report problems in a way that gets them fixed.

Open source is also one of the best places to practice engineering in public. Reading unfamiliar code, proposing a change, defending it in review and accepting feedback are the same skills a team requires, with the added benefit that your work is visible and verifiable. At the other end, maintaining a project teaches scope control, communication and the cost of every feature you accept.

## What you will learn

- How to find a first contribution, prepare it well and get it merged.
- What maintainers do, and how to run a project without burning out.
- How license families differ, and how to avoid common compliance mistakes.
- How communities make decisions, and how governance fails.
- How to evaluate and defend against supply chain risk in open source dependencies.

## Prerequisites

- Comfort with Git and pull requests. See [Developer Tools](../15-developer-tools/README.md).
- Basic security vocabulary. See [Security](../10-security/README.md).
- Willingness to read code written by strangers.

## What good looks like

- You read the contribution guide and search existing issues before opening anything.
- You keep changes small, focused and tested, and explain the reason for them.
- You respond to review feedback without defensiveness and without disappearing.
- You check the license of every dependency before adding it.
- You can state, in plain terms, the obligations your chosen license places on users.
- You pin, review and monitor dependencies instead of installing whatever resolves.
- If you maintain a project, you publish a scope, a code of conduct and a security policy.
- You treat maintainer time as a limited resource and ask for help accordingly.
